# Marketplace Development Log — August 2026

## 2026-08-28 (later) — Marvelous Ifezue (Claude Code)

**What changed**: Implemented the full order/delivery/seller/deliverer/escrow system specified in the follow-up implementation request — the largest single change to the Marketplace to date. Schema: added `OrderStatus`, `FulfillmentStatus`, `DeliveryStatus`, `OrderDeliveryOutcome`, `DeliveryAttempted`, `EscrowPaymentStatus`, `PayoutStatus`, `DelivererStatus`, `DayOfWeek`, `FineStatus`, `OrderEventType` enums; `Deliverer`, `Delivery`, `DeliveryItem`, `Delivery_x_businesses`, `OrderEvent`, `BusinessDeliveryDay`, `LateDeliveryFine` models; extended `Order`, `OrderItem`, `Business`; dropped the dead order-level OTP/escrow columns in favor of item-level equivalents; re-added `Business.bankCode` (previously removed, now needed for Paystack payouts). Two migrations applied to the local dev database, including a hand-written data migration for the one pre-existing `Order` row's `status` value.

Backend: `src/lib/{estimated-delivery,dropoff-deadline,otp,order-events,escrow,seller-payout,late-delivery-fine,deliverer,admin,cron-auth,seller-order-sections}.ts`; ~25 new API routes covering seller accept/reject/ready/drop-off, item-level rejection, late-fine payment (Paystack), deliverer application/status/handoffs/deliveries, admin deliverer approval and delivery-coordinator assignment, buyer order tracking, and five `/api/cron/*` routes. Extended `src/lib/external/paystack.ts` with transfer-recipient creation and transfer initiation. Extended `services/marketplace/notifications/email.service.ts` with 14 Resend-backed templates. Rewrote `services/marketplace/checkout/checkout.service.ts` to use the new enum, compute/persist estimated delivery at checkout, and trigger the new-order seller email.

Frontend: rewrote the seller Orders tab into the five-section dashboard with action buttons and a fine-payment banner; added a delivery-days picker to business onboarding/edit; added the buyer order-tracking page, the Deliverer Dashboard, the deliverer application page, and two admin pages (deliverer approval, delivery assignment); updated the footer to reflect the deliverer application lifecycle; added estimated-delivery display to the product modal and checkout page.

**Why**: Direct implementation request specifying the full workflow (buyer → business/seller → central drop-off → delivery coordinator → deliverer → buyer → escrow → seller payout), with an explicit instruction to compare the result against the existing documentation and keep both in sync.

**Files/systems affected**: See the new/rewritten files under `docs/marketplace/systems/`, `docs/marketplace/data/`, `docs/marketplace/decisions/`, and updated TODO phases 2-8 — too many source files to list individually here; the doc set above is the index.

**Important implementation details**:
- Resolved two real conflicts against the earlier documentation pass rather than silently picking one side: (1) `PENDING_SELLER` vs. the earlier "use PENDING, not PENDING_SELLER" guidance — the later, more detailed, repeatedly-stated implementation spec won; recorded in [`../decisions/pending-seller-terminology-changed.md`](../decisions/pending-seller-terminology-changed.md). (2) Reintroducing `Business.bankCode`, previously deliberately dropped by an earlier migration when nothing needed it — recorded in [`../decisions/business-bank-code-reintroduced.md`](../decisions/business-bank-code-reintroduced.md).
- Escrow and OTP state were moved from `Order` (where dead, unused columns already existed) to `OrderItem`, since the actual requirement (item-level escrow, per-item delivery OTP) needs item granularity — the old Order-level columns were dropped rather than left alongside the new ones, to avoid two competing sources of truth.
- Caught and fixed a self-introduced bug during the pass: the deliverer application route initially blocked reapplication for a `REJECTED` applicant (via `Deliverer.userId`'s unique constraint) while the footer's own documented behavior claimed rejection wasn't permanent — fixed by having reapplication update the existing row back to `PENDING` rather than blocking it. See [`../decisions/rejected-deliverer-can-reapply.md`](../decisions/rejected-deliverer-can-reapply.md).
- Two infrastructure decisions were confirmed with the user before writing code, since neither was derivable from the existing codebase: Vercel Cron + authenticated routes for scheduling (over an in-process `node-cron`), and Resend for email (over SMTP or a stub). See [`../decisions/cron-mechanism.md`](../decisions/cron-mechanism.md), [`../decisions/email-provider.md`](../decisions/email-provider.md).

**Testing performed**: `npx tsc --noEmit` clean across the whole codebase; a full `npm run build` (Next.js production build, including its own TypeScript pass and static generation for all 44+ routes) completed successfully; `npm run lint` clean for every file touched in this pass (4 pre-existing lint errors in untouched files — `studashboard/page.tsx`, `use-theme-preference.ts` — were confirmed pre-existing via `git diff`, not introduced here). No runtime/integration testing was performed (would require a live Paystack test-mode transaction and Resend API key) — see the honest gaps below.

**Issues encountered / resolved**: The reapply bug above (resolved). A React `react-hooks/set-state-in-effect` lint violation in four new pages, fixed by following the exact pattern already established in `useCart.ts` (a locally-defined wrapper function inside the effect, rather than calling an outer reusable loader directly).

**Remaining issues** (see `todo/phase-05-escrow-and-payments.md` and `todo/phase-08-testing-and-hardening.md` for the full list): refunds don't yet call a real Paystack refund API (the state machine is real, the reversal transfer isn't); no Paystack transfer-webhook handler for a payout that doesn't resolve synchronously; delivery windows are one fixed constant, not business-configurable; delivery restriction isn't enforced beyond the dashboard warning; the pre-existing stock-reservation gap is still open; no automated test suite exists for any of the new money-handling logic.
