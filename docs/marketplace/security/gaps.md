# Security: Known Gaps

This is a working-code assessment, not a "the app is insecure" claim — it lists things a maintainer should be aware of before scaling the Marketplace up, per the instruction to document real gaps rather than assume something is secure just because it currently works.

- **No stock reservation at checkout.** `Product.stock` is never decremented by order creation or payment confirmation. Two buyers can both successfully pay for the last unit of a product; nothing in the code detects or prevents this. Fixing this needs either a stock decrement inside `createOrdersForCheckout`'s transaction (with a guard against going negative) or a reservation/hold mechanism.
- **No rate limiting** on any route, including ones that call external APIs (`checkout/verify` → Paystack verify call, `paystack/resolve-account`, `uploads` → Cloudinary). A scripted client could hammer these.
- **Cart clearing on payment confirmation is "clear everything," not "clear what was paid for."** If a buyer adds a new item to their cart during the payment gap, `confirmPaymentByReference` deletes it too, silently. Low severity (nothing is charged incorrectly — the buyer just has to re-add the item) but worth fixing before cart abandonment/multi-tab usage becomes common.
- **No schema-level input validation library.** Required-field/type checks are hand-written per route. Consistent today by convention, but there's nothing enforcing a new route follows the same pattern — a missed check would be a silent gap, not a caught error.
- **`Order.status`/`paymentStatus` are free-text strings, not a Prisma enum.** Nothing in the database prevents an errant future write from introducing a typo'd or unexpected status value that other code doesn't recognize.
- **Plaintext bank details.** `Business.bankName`/`accountNumber`/`accountHolderName` are stored unencrypted. Not exploitable for direct fund transfer on their own, but is sensitive PII that a database-level breach would expose.
- **`GET /api/marketplace/businesses/featured` and `GET /api/marketplace/search/products` require sign-in but not ownership** — this is intentional (public browse), not a gap, but is called out here so it isn't mistaken for one during a future audit.
- **No audit/event log** for who changed what business/product/order data and when — see [`../todo/phase-08-testing-and-hardening.md`](../todo/phase-08-testing-and-hardening.md).
- **Webhook route has no dead-letter/retry-tracking of its own** — it relies entirely on Paystack's own retry behavior for a non-2xx response. If `confirmPaymentByReference` throws for a reason unrelated to Paystack (e.g. a transient DB outage), the failure is invisible unless someone is watching server logs and Paystack's own webhook delivery dashboard.
- **Refunds aren't actually reversed at Paystack.** `services/marketplace/escrow/escrow.service.ts#refundOrderItem` moves an item straight to `REFUNDED` without calling a real Paystack refund API — the state machine is real, the money movement behind it isn't yet. See [`../systems/escrow-system.md`](../systems/escrow-system.md) and [`../todo/phase-05-escrow-and-payments.md`](../todo/phase-05-escrow-and-payments.md).
- **No Paystack transfer-webhook handling.** A transfer that comes back `pending`/`otp` (not immediately `success`) is left `PAYOUT_PROCESSING` indefinitely — there's no `transfer.success`/`transfer.failed` webhook handler to resolve it later. See [`../systems/seller-payout-system.md`](../systems/seller-payout-system.md).
- **Delivery restriction isn't actually enforced anywhere else.** `Business.deliveryRestricted` is set correctly and surfaced in the seller dashboard, but nothing currently blocks a restricted business's orders from proceeding through drop-off/coordinator assignment — see [`../systems/late-delivery-fine-system.md`](../systems/late-delivery-fine-system.md).
- **Deliverer-inventory/delivery-schedule crons have no idempotency guard against being run twice in the same window** — a duplicate midnight run would send a duplicate digest email to every deliverer. Low risk given Vercel Cron's own scheduling reliability, but not defended against in code.
- **OTP routes aren't rate-limited at the route level** — bounded per-OTP by the 5-attempt counter (`src/lib/otp.ts`), but an authenticated deliverer could still make many requests in quick succession across different items/OTPs. See [`otp-security.md`](otp-security.md).
