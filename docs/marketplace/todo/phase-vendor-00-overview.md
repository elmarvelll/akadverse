## Honest gaps — not implemented, not silently skipped

- **Active alerting/escalation**: vendor no-show, deliverer no-show/late, delivery-window expiry, and capacity conflicts are all *visible* through the existing Orders/OrderEvent/Bookings/Disputes views, but nothing here pushes a proactive admin notification for them (spec §29/43/44/50/63 ask for "Vendor Manager is alerted"). Would need new detection logic (e.g. a cron flagging orders stuck `OUT_FOR_DELIVERY`/`HANDED_TO_DELIVERER` past their window) plus `notifyAdmins()` calls — the plumbing (`notifyAdmins`, `AdminActionLog`) exists and is proven elsewhere in this feature, this is additional cron/detection work, not infrastructure work.
- **Delivery-window-expiry finalization** (spec §50): only the *post-delivery* 24h dispute window has a cron. An order stuck `OUT_FOR_DELIVERY`/not yet marked delivered once its slot's window has fully passed is not automatically flagged or force-resolved.
- **Explicit VENDOR_LATE/VENDOR_NO_SHOW/DELIVERER_LATE/DELIVERER_NO_SHOW operational states**: the enum values exist in `OrderEventType`/`DeliveryStatus` conceptually reusable, but no dedicated action/UI marks a vendor or deliverer late/no-show, nor computes lateness automatically against `vendorPrepDeadlineMins`/30-min arrival.
- **Buyer-unavailable / return-to-drop-off**: reuses the existing generic `DELIVERY_ATTEMPTED`/`FAILED`/`RETURNED` machinery (already built for Business); no vendor-specific "returned to central drop-off, here's the financial policy" wiring was added on top.
- **Real Paystack refund/transfer-webhook calls**: matches a pre-existing, already-documented Business gap (`docs/marketplace/security/gaps.md`) — a refund/payout is treated as complete once initiated/transferred successfully; a provider-side async failure after that point isn't caught by a webhook (none exists for Business payouts either). Not introduced by this work, not silently duplicated further.
- **Automated tests**: none written. Every phase was verified via `tsc --noEmit`, full-repo `eslint`, and `next build` passing cleanly, matching the existing codebase's own testing posture (`docs/marketplace/todo/phase-08-testing-and-hardening.md` records the same gap platform-wide) — not via unit/integration tests or a live end-to-end run (no dev server was started, no real Paystack test payment was simulated).
- **Deliverer payout attempts cap**: `delivererPayoutAttempts` has no cap enforced *in* `process-deliverer-payout.ts` itself (only in the sweep's retry-selection query) — matches `process-item-payout.ts`'s identical structure.
