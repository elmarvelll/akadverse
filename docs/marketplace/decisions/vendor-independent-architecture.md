# Decision: Vendor is a structurally independent feature, and vendor capacity ≠ deliverer roster capacity

- **Date**: 2026-09-06.
- **Context**: The first School Vendor build (see `vendor-extends-business.md`) implemented Vendor as a `Business.type = "SCHOOL_VENDOR"` discriminator, reusing the Business owner dashboard (`business/[id]/products`, etc. with vendor-only conditionals) and Business's product API routes for vendor product management. It also used one field, `VendorDeliverySlot.delivererCapacity`, for two different purposes: gating how many customer orders could book a timeframe, and (intended, not yet built) how many deliverers admin could roster for it. Vendor pickups were routed through Business's central-coordinator drop-off chain (`Order.dropoffOtp` → coordinator confirms → coordinator assigns deliverer → deliverer picks up from the coordinator).
- **Correction, superseding the earlier decision**:
  1. **Vendor gets its own dashboard route tree and its own product/variant API routes** — `vendor-dashboard/[id]/*` and `/api/marketplace/vendor/[id]/products/*` — rather than living inside Business's pages/APIs with type conditionals. Genuinely generic, non-Business-specific helpers (`services/marketplace/product/shared/*`, which already operate on `Product`/`ProductVariant`/`ProductImage` with no Business-specific logic) are still reused by the new vendor-owned service layer — only the route/page/controller ownership changed, not the underlying data model or every helper.
  2. **Vendor capacity and deliverer-roster capacity are two independent systems.** New `VendorTimeframeCapacity` (businessId, slotId, capacity) is the vendor's own "how many orders can I fulfill in this window" ceiling, vendor-configured, checked only at booking time. `VendorDeliverySlot.delivererCapacity` keeps its field but is redefined to mean only "how many deliverer roster positions admin has configured for this timeframe" — it must never be read in the booking/checkout path again. New `DelivererRosterAssignment` (delivererId, slotId, date, status) is the admin-managed schedule of who's on duty, independent of specific orders.
  3. **No central drop-off for vendor.** The existing OTP primitive (`Delivery_x_businesses.pickupOtp`, `confirm-pickup.ts`) is reused unchanged, but the vendor's own ready order skips the seller→coordinator drop-off confirmation entirely (there is no coordinator step for vendor) — the vendor marks an order ready, admin assigns a deliverer directly, and the resulting pickup OTP is shown to the **vendor** (at their own dashboard) rather than a coordinator, and is entered by the deliverer once they physically reach the **vendor's own location** (`Business.location`), not a central point.
- **Why**: this matches the explicit product requirement that Business and Vendor be independently structured features that happen to share underlying data models and infrastructure, not one feature with a type flag threaded through shared UI/API. It also fixes a real correctness bug: without this split, admin raising/lowering deliverer roster capacity would have silently changed how many customers could book a vendor's timeframe, and vice versa — two operationally unrelated decisions were coupled through one field.
- **Consequences**: `business/[id]/products` reverts to Business-only (no "Add Sides" button, no vendor-type branching). The vendor Sides page moves (not duplicates) from `business/[id]/sides` to `vendor-dashboard/[id]/sides`. `create-vendor-orders-for-checkout.ts`'s capacity check changes from a single global count against `slot.delivererCapacity` to a per-vendor-in-cart count against that vendor's own `VendorTimeframeCapacity` row. `READY_ITEM_WHERE` gets a vendor-aware branch so a vendor `OrderItem` is pickup-eligible as soon as the vendor marks it ready, without requiring the Business-only `sellerDroppedOffAt` coordinator-confirmation field.
