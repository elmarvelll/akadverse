# Decision: `Business.bankCode` is re-added, reversing an earlier removal

- **Date**: 2026-08-28.
- **Context**: A prior migration (`20260827145403_remove_business_bank_code`) dropped `Business.bankCode` — at that time nothing needed it; the bank *name* was enough to display, and the bank code was only used transiently in the onboarding form's own local state to call Paystack's account-resolution endpoint.
- **Problem**: The seller-payout system now needs to create a Paystack transfer recipient for a business, which requires the bank **code**, not the display name — there is no reliable way to derive a bank's code from its name at payout time without persisting it (bank lists can be refreshed/reordered by Paystack; matching by name string is fragile).
- **Chosen option**: Re-add `Business.bankCode` (migration `20260828163000_business_bank_code_for_payouts`), and have `BankDetailsFields.tsx` persist it (previously it deliberately did not, per its own prior comment).
- **Reason**: The prior removal was correct *for what existed at the time* — it wasn't a mistake, it was a decision that a fact (payouts don't exist yet) later stopped being true. This decision doesn't erase that — it records why the constraint changed. Per the documentation's own decision-maintenance rule, this file exists alongside (not instead of) the historical migration that removed the column.
- **Consequences**: An existing `Business` row created before this change has `bankCode = null` even if it has a `bankName`/`accountNumber` set — its owner needs to re-select their bank once (or the app needs a backfill pass matching stored `bankName` against Paystack's bank list) before a payout can succeed for it. `services/marketplace/payout/seller-payout.service.ts#processItemPayout` fails loudly (`payoutStatus = PAYOUT_FAILED`, reason recorded, seller emailed) rather than silently for a business missing `bankCode`.
- **Alternatives rejected**: Resolving `bankCode` from `bankName` at payout time via a fresh Paystack bank-list lookup — rejected as fragile (relies on exact name matching against a list that could change) and unnecessarily re-fetches data that's cheap to just store once.
