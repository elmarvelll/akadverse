# Decision: SSE notification polling must not compound DB connection contention

- **Date**: 2026-09-06.
- **Context**: Marketplace API requests were intermittently taking 3-10 seconds, and the notification SSE stream was occasionally producing `unhandledRejection` errors. Root cause, confirmed via a `PrismaClientKnownRequestError P2024` ("Timed out fetching a new connection from the connection pool"): `DATABASE_URL` had `connection_limit=1` explicitly set in the connection string, meaning Prisma's client-side pool to Supabase's transaction-mode pgbouncer (port 6543) was capped at exactly one physical connection for the entire app. Every concurrent query — cart, products, business dashboard, notifications, deliverer status, etc — serialized through that single connection; the notification SSE stream's 5-second polling loop (`prisma.notification.findMany`, one query per open connection per 5s) made this worse by holding the one connection at a regular cadence indefinitely for the lifetime of the stream, on top of ordinary request traffic.
- **Problem**: with `connection_limit=1`, any query issued while another is in flight queues for up to `pool_timeout` (Prisma default: 10s) before failing with P2024. The SSE poll's `setInterval` callback also had no `try/catch`, so a P2024 there surfaced as a raw `unhandledRejection` instead of a recoverable, logged failure — and had no overlap guard, so if one poll took longer than the 5s interval (likely exactly when the pool was already contended), a second poll could start on top of it, worsening contention further.
- **Fix**:
  1. `DATABASE_URL`'s `connection_limit` raised from `1` to `10` (with `pool_timeout` raised from the 10s default to 20s as a safety margin), giving the app a small-but-real pool against Supabase's transaction pooler — which is designed specifically to multiplex many such client connections, so this is well within normal usage for a single Next.js server process, not a value chosen to "just make errors go away." `DIRECT_URL` (migrations only, `prisma migrate` — infrequent, effectively sequential) was left untouched.
  2. `notifications/stream/route.ts`'s poll now wraps its query in `try/catch` (logs and continues on failure — a poll failing must never take down the whole SSE connection) and a `polling` boolean guard so a slow poll can't overlap with the next interval tick.
  3. Fixed a related, separately-discovered bug in the same file: the `ReadableStream`'s `cancel()` callback (invoked by the platform on some client-disconnect paths that don't fire `request.signal`'s `abort` event) set `closed = true` without ever actually clearing the `heartbeat`/`poll` intervals or unsubscribing from the broadcaster — and because the shared `cleanup()` function's own guard checked that same `closed` flag, a `cancel()`-first disconnect meant `cleanup()` would forever after silently no-op if called from `abort` too. `cleanup` is now lifted to a scope shared by both `start()` and `cancel()`, and both paths call the same idempotent teardown.
  4. Added a temporary, env-gated (`DB_TIMING_DEBUG=1`) diagnostic: `src/lib/prisma.ts` logs each query's engine-reported execution duration (excludes pool-queueing time) when enabled, and the SSE poll logs its own wall-clock total — comparing the two isolates how much of any remaining slowness is pool contention versus the query itself. Safe to delete once pool sizing is confirmed stable; zero-cost when the env var is unset.
- **Deliberately not done**: `connection_limit` was not raised to an arbitrary large number (e.g. 20-50) — the right ceiling depends on the actual Supabase plan's total connection budget, which wasn't verified against the dashboard here. 10 is a conservative starting point for one Next.js dev server process, not a value that assumes headroom this session couldn't confirm. If P2024 recurs at higher real concurrency, check Supabase's pooler settings (pool_mode, default_pool_size) before raising this further.
- **Not converted to push-only delivery**: the existing broadcaster (`sse-broadcaster.ts`) already delivers same-instance notifications instantly, with the DB poll as a fallback for a notification created on a different server instance — this was already the intended architecture (see the file's own header comment), not something introduced by this fix.

## Follow-up (same day): checkout was the real pool-starvation trigger, plus a second latent bug

After the pool/SSE fix above, P2024 and a new `P1017` ("Server has closed the connection") recurred, now during `vendor-checkout/initialize` specifically. Root-caused two additional, distinct issues:

1. **N+1 round trips inside a held transaction**: `create-vendor-orders-for-checkout.ts`'s booking transaction did one `findUnique` + one `update` per cart item, plus one `findUnique` per distinct vendor — for a small 3-item, 2-vendor cart, ~13 sequential round trips, all inside one Postgres transaction holding one pooled connection for its entire duration. Against a remote (non-co-located) database, each round trip pays real network latency, so this transaction alone could run for many seconds while occupying a connection every other concurrent request needed. **Fixed**: batched the per-item reads into 3 bulk `findMany` calls (one per entity type: Side/ProductVariant/Product) keyed by `id: { in: [...] }`, and the per-vendor check into one bulk `findMany` — identical validation logic and atomicity guarantees, far fewer round trips. Decrements remain individual `update` calls (each decrements a different amount; this is the actual write Serializable isolation needs to see per-row).
2. **Prisma's default interactive-transaction timeout (5000ms) was never overridden** on this transaction. Verified directly: under network latency, the *un-batched* transaction shape exceeded that budget and Prisma killed it outright with `P2028` ("Transaction already closed") — a distinct failure mode from P2024, not something more `connection_limit` would fix, since the transaction itself was still running when Prisma gave up on it. **Fixed**: added explicit `maxWait: 10000, timeout: 15000` to the `$transaction` call — enough headroom for real round-trip latency post-batching, still bounded (a genuinely stuck transaction still fails rather than holding its connection forever).

**Polling frequency reduced**: the SSE fallback poll (see above) was 5s; raised to 20s. It's a fallback for a cross-instance-created notification, not the primary path (the broadcaster delivers same-instance notifications instantly) — a fallback doesn't need sub-5-second responsiveness, and every open SSE connection ran this query on its own independent timer regardless of whether anything had changed. Delivery semantics (eventual delivery, dedup via `sentIds`) are unchanged; only the fallback path's worst-case delay grew.

**Verified with a direct load test** (bypassing HTTP/auth, using the app's real Prisma client): with a warm pool, a realistic post-fix checkout-shaped transaction (11 round trips, Serializable, `maxWait`/`timeout` as above) ran for ~4s while 5 concurrent lightweight reads (shaped like cart/products/businesses/notifications/deliverer-status) all completed in ~670ms *during* that same window — zero P2024, zero P2028, zero P1017. Under the original `connection_limit=1`, this concurrent completion was structurally impossible; the lightweight reads would have queued behind the transaction's single connection.

**P1017 diagnosis**: not treated as a separate bug requiring its own fix. It's consistent with Supabase's Supavisor pooler forcibly resetting connections once the pool is already thrashing under P2024 pressure — a secondary symptom of the same root cause (contention), not an independent failure mode. It did not recur in the load test above once the underlying contention was addressed.

**Note on `create-orders-for-checkout.ts`** (the Business checkout, a sibling file this work deliberately never modifies — see `vendor-extends-business.md`): it has the same per-item sequential read+write pattern inside its own transaction. Not fixed here (out of this fix's scope and explicitly walled off from vendor-side changes), but it will produce the same pool-pressure symptom under Business-checkout load and should get the same batching treatment if it becomes a problem.
