# Student portal and productivity audit (before implementation)

The active portal is `src/app/studashboard/page.tsx`, using clickable divs and imperative navigation without transition feedback. Marketplace, Productivity and E-Learning point at existing protected routes. E-Learning student navigation still exposes Results and GPA/CGPA; the student dashboard also queries and displays CGPA. Academic History includes the same GPA output. Faculty/HOD results infrastructure is independent and must be retained.

The active Schedule Manager is under `src/features/productivity/schedule`, not the separate `schedule-manager/` project. Its existing day/week grid already supports overlap lanes, multiple cards, midnight splitting and timezone conversion. It reads ProductivityEvent rows plus approved academic timetable data. Ordinary task inputs contain only a deadline, with no working interval; task creation cannot currently populate the grid. Task invalidation excludes the schedule cache. New task cache merging only considers today's workload. Event/habit timelines, TaskService and assistant tools must all preserve the same owner boundary.

Core Prisma models are ProductivityTask, ProductivityEvent, ProductivityHabit, ProductivityOccurrence, ProductivityCategory, ProductivityPreferences and ProductivityRequest. JSON data stores canonical domain fields; task outcome and dueDate have indexed mirrors. Events have owner-scoped category/linkedTask/occurrence relations. Occurrences are unique by habit/date and their task/event relations are unique. Mutation receipts provide idempotency. Existing API is POST /api/productivity; owner is derived from authentication, never submitted task data. View projections use request-local range loading, shared client cache, and source services. No additional event/task table is needed for a scheduled task.

Event failure reference 1739b3ac-ce1d-4744-bd95-f105b3175fa5 logged Prisma P2024 in academic.registrations (10.5 seconds). The prior fix removes lecturer identity resolution under an already-pinned Core mutation transaction; approved timetable conflict validation remains. The phase wraps multiple queries so this is a verified starvation risk, not conclusive proof of which database was exhausted. Session pool saturation remains an independent deployment risk. Further remediation must not convert failed timetable reads into successful conflict checks.

PIP currently uses AssistantPanel, authenticated assistant routes/service callbacks, persisted conversations/tool executions/confirmation proposals, signed delegations and a separate Python Gemini orchestrator. The HTTP flow is non-streaming. Messages are plain paragraphs; existing Markdown dependencies are available. Voice input uses the existing speech controls. A durable outcome fallback already exists and must remain. The screenshots share rounded light surfaces, blue/purple accents, a friendly robot, readable message bubbles, and a pinned composer. The requested PIP design excludes canned task/habit creation buttons despite some reference images including them.

Study Zone and classroom still display Stuwart. Internal StuwartPanel identifiers, /stuwart API paths, stewart storage/config keys and database/provider contracts are compatibility identifiers and must not be blindly renamed. PIP must retain its separate identity.

Existing cron jobs handle inventory/delivery, AI ingestion and revision generation; productivity notifications and recurrence are existing services, not a reason to introduce another scheduler. No new notifications, reminder promises, cron jobs or external providers are needed. Relevant testing infrastructure includes productivity unit/memory integration tests, local-only DB persistence suites, platform navigation tests, Python assistant tests, and isolated Chromium browser fixtures. Test helpers refuse non-local databases. No production test records should be created.

Implementation choice: add an optional validated scheduledSlot to existing task JSON, project scheduled tasks directly into calendar cards, preserve deadline semantics, and invalidate affected calendar caches. No schema migration is required. Unsized/date-only tasks remain outside time slots. Display-only changes must preserve authorization, real tools, pending confirmations and receipt replay.
