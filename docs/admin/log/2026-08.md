# Admin Development Log — August 2026

## 2026-08-28 — Marvelous Ifezue (Claude Code)

**What changed**: Implemented the full Admin Dashboard: schema (`Business.verified`/`blocked` fields, `BusinessReport`, `AdminActionLog`, two new `OrderEventType` values), 21 new admin API routes (route → controller → service, one action per service file, matching the codebase's established convention), 8 admin dashboard pages plus a shared layout/nav, and two small buyer-facing additions (report a business, dispute an order) needed to make the Disputes/Reports tabs real rather than permanently empty. Two migrations applied to the local dev database (the second one fixing a relation I initially got wrong — see below).

**Why**: Direct implementation request for admin oversight of the Marketplace — users, business verification/blocking, disputes, order history, fines, reports — following the existing route/controller/service architecture rather than inventing a parallel one.

**Files/systems affected**: See `docs/admin/systems/` for the full index. Backend: `services/marketplace/admin/**` (new), `services/marketplace/business/report-business.ts` (new), `services/marketplace/order/dispute-order.ts` (new), `src/lib/admin.ts` (kept as-is, reused unchanged), `src/lib/controller-helpers.ts` (unchanged, reused), `src/app/api/marketplace/admin/**` (new, 21 routes), `src/app/api/marketplace/businesses/[id]/report/**` and `src/app/api/marketplace/orders/[id]/dispute/**` (new). Frontend: `src/app/studashboard/admin/marketplace/**` (layout, 8 new pages, 2 shared components), `ProductDetailModal.tsx` and `orders/page.tsx` (buyer-facing additions), `deliverers/page.tsx` and `deliveries/page.tsx` (adjusted to use the new shared layout instead of their own `DashboardNavbar`).

**Important implementation details**:
- Two decisions were confirmed with the requester before writing code, since neither was derivable from the codebase alone: (1) the dashboard requires `super_admin` — reusing `requireAdmin()` exactly as it already stood, rather than reverting its recent narrowing from `admin`+`super_admin`; (2) Disputes and Reports needed new, minimal buyer-facing triggers ("Dispute this order," "Report business") rather than staying admin-view-only against columns/tables nothing could ever populate. See `docs/admin/decisions/`.
- `BusinessReport.reporterId` was initially written as a bare string with a manual second query to resolve the reporter's email in `list-reports.ts`. Caught before considering the work done: reconsidered against the rest of the schema's convention (real relations for anything routinely joined through) and fixed to a proper `@relation` to `User`, which required a second migration adding the foreign key after the table already existed. `npx prisma generate` also had to be re-run after that schema edit — the first `next build` after adding the relation failed with three `TS2561`/`TS2551` errors pointing at the stale generated client, which is what caught the missed regenerate.
- `Order.isDisputed` and its sibling columns existed from an earlier pass but were completely dormant (confirmed by grep before starting) — this is the first code that ever writes to them.
- Reused the exact `window.prompt()` reason-entry pattern already established for reject/suspend/block flows elsewhere in the Marketplace, rather than introducing a new modal component, for the two new buyer-facing actions and the block/resolve/reject admin actions.

**Testing performed**: `npx prisma migrate deploy` + `generate` clean; full `next build` (compiles and type-checks all 21 new + 2 buyer-facing routes, plus every existing route) clean; `npm run lint` clean except the 2 pre-existing, untouched errors. Live check: started the production build locally and `curl`'d `/api/marketplace/admin/overview` and the promote-user route with no session cookie — both returned `401 {"error":"Not authenticated."}`, confirming the unauthenticated case is rejected before reaching any controller logic. Verified by grep that every one of the 21 admin `route.controller.ts` files calls `requireAdmin()` — none skip it.

**Issues encountered / resolved**: The `reporterId` relation fix above (resolved). The stale-Prisma-client build failure after adding that relation (resolved by re-running `prisma generate`). Two ESLint `Unused eslint-disable directive` warnings on pages where the `react-hooks/exhaustive-deps` suppression wasn't actually needed (removed).

**Remaining issues**: See `docs/admin/todo/phase-01-admin-dashboard.md` — highest-priority: `Business.blocked` isn't enforced anywhere outside the admin UI itself yet; no demotion path; no email notifications for any admin action; the wrong-role (403) path wasn't tested live end-to-end (only verified by code inspection + the same mechanism's 401 path being live-tested).

## 2026-08-28 (later) — Marvelous Ifezue (Claude Code)

**What changed**: Replaced the role-based admin gate (`role === "super_admin"`) with an independent `User.isAdmin` boolean, per direct request — a student, faculty, admin, or super_admin account can now independently also be an admin, rather than admin access requiring a specific role value. Removed `src/app/superadmindashboard/` (the role-based portal this superseded) and updated `src/proxy.ts`'s `ROLE_HOME_PATHS` so `role: "super_admin"` now lands on the normal student home like any other role without a dedicated portal. Added a symmetric `revoke-admin.ts`/"Remove admin" action alongside the existing grant action — closing the "no demotion path" gap noted when the dashboard first shipped, since a boolean flag naturally wants both directions implemented.

**Why**: Direct implementation request — see the chat for the exact wording. The core ask was that admin-ness be a second, independent attribute of a user rather than a distinct role/portal.

**Files/systems affected**: `User.isAdmin` (new field, migration `20260828180000_user_is_admin_flag` with a data backfill for the existing `super_admin`-role account), `src/lib/auth.ts` (jwt/session callbacks now carry `isAdmin`), `src/types/next-auth.d.ts` and `src/context/AuthContext.tsx` (type augmentation), `src/lib/admin.ts#requireAdmin` (checks the flag, not the role), `services/marketplace/admin/{promote-user-to-admin,revoke-admin,search-users,get-user-detail}.ts`, new route `.../users/[userId]/revoke-admin`, `src/app/studashboard/admin/marketplace/users/page.tsx` (grant/revoke UI, role badge shown separately from an Admin badge), `src/app/studashboard/page.tsx` (Admin card condition), `src/app/components/dashboard/shared/ComingSoon.tsx` (stale portal-list comment fixed).

**Important implementation details**:
- The data backfill (`UPDATE User SET isAdmin = true WHERE role = 'super_admin'`) was written and applied specifically so the one real admin account in the dev database (confirmed by query before writing the migration) didn't lose access as a side effect of the mechanism change.
- `Role` enum itself was deliberately left unchanged (still has `student`/`faculty`/`admin`/`super_admin`) — removing `super_admin` from it would have been a larger, riskier change than what was asked, and nothing currently requires it.
- `role: "admin"`'s existing `/admindashboard` placeholder was left untouched — out of scope, not mentioned in the request.

**Testing performed**: Full `next build` clean; `npm run lint` clean except the 2 pre-existing, untouched errors. Live check: started the production build and `curl`'d `/api/marketplace/admin/overview` and the new revoke-admin route with no session — both returned `401 {"error":"Not authenticated."}`. Confirmed by direct database query that the pre-existing `super_admin` account has `isAdmin: true` after migration.

**Issues encountered / resolved**: A `next start` run initially failed with a missing `prerender-manifest.json` because an earlier `npm run build | head -15` had been piped and the build's output was truncated mid-write by the pipe closing early — not a real build failure, just an artifact of how the check was run. Resolved by re-running the full build without truncating the output.

**Remaining issues**: See `docs/admin/security/authorization.md`'s Known Gaps — notably, no UI safeguard against revoking your own last-remaining admin access (would need direct database access to recover from).
