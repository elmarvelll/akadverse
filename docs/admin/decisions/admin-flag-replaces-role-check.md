# Decision: Admin access is a `User.isAdmin` flag, not the `super_admin` role

- **Date**: 2026-08-28.
- **Context**: [`admin-access-level.md`](admin-access-level.md) recorded the earlier decision — the Admin Dashboard requires `role === "super_admin"`, reusing `requireAdmin()` exactly as it stood. That tied admin access to the platform's single-role model: one `Role` enum value per user, and it also implied a separate `/superadmindashboard` portal for that role.
- **Problem**: The single-role model can't express "this student is also an admin" or "this faculty member is also an admin" — someone needing admin access had to actually become a `super_admin`, changing what portal they land on and displacing whatever role they actually held (student, faculty). The request was explicit: two independent things should be true of a user at once — their normal role, and whether they're an admin.
- **Chosen option**: Add `User.isAdmin Boolean @default(false)`, independent of `role`. `requireAdmin()` now checks `session.user.isAdmin` instead of `session.user.role === "super_admin"`. The Admin card on the home route (`studashboard/page.tsx`) is shown based on the same flag. `src/app/superadmindashboard/` (the role-based portal) is removed; `role: "super_admin"` now routes to the normal student home (`/studashboard`) like any other role that has no dedicated portal built, per `src/proxy.ts`'s `ROLE_HOME_PATHS`.
- **Reason**: Directly matches the request, and is a cleaner model regardless — "what portal am I in" (role) and "do I have admin oversight access" (a permission) are genuinely orthogonal concerns that the old design conflated.
- **Consequences**:
  - Existing `role: "super_admin"` accounts had their access preserved by a one-time data migration (`UPDATE User SET isAdmin = true WHERE role = 'super_admin'`) rather than silently losing admin access — see [`../data/schema.md`](../data/schema.md).
  - `promote-user-to-admin.ts` now sets `isAdmin = true` (never touches `role`); a new `revoke-admin.ts` sets it back to `false` — a flag needed a symmetric "un-grant" action in a way a role value arguably didn't (this also closes the "no demotion path" gap noted in the dashboard's original TODO).
  - `role: "super_admin"` still exists in the `Role` enum (not removed — a bigger, riskier change than what was asked, and nothing currently depends on removing it) but no longer carries any Marketplace admin meaning by itself. A `super_admin`-role account with `isAdmin: false` has no more access than any other role.
  - `role: "admin"` and its `/admindashboard` placeholder are untouched — unrelated to this change, not mentioned in the request.
- **Alternatives rejected**: Keeping `role`-based admin and just widening it back to `admin`-or-`super_admin` (the option rejected in the original `admin-access-level.md` decision) — rejected again here for the same reason plus a new one: it still can't express "a student who is also an admin," which is the actual requirement.

This decision supersedes [`admin-access-level.md`](admin-access-level.md)'s specific mechanism (the *which role* question) while keeping its underlying reasoning (avoid a second, competing authorization scheme) — that file is kept, not deleted, per the documentation's own decision-preservation rule.
