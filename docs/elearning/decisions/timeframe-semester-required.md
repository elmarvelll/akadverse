# Decision: `AcademicTimeFrame.semesterId` is required, not nullable

- **Date**: 2026-09-14.
- **Context**: `AcademicTimeFrame` was originally modeled with `semesterId String?` — a deadline like Course Registration is naturally per-semester in every real usage, but nothing in §27 strictly requires one, so it was left optional "to not force every timeframe type into the same shape."
- **Problem**: `@@unique([type, academicSessionId, semesterId])` with a nullable `semesterId` doesn't work — Postgres/Prisma's composite-unique `where` selectors don't accept `null` for a field in a compound unique key (NULL is never equal to NULL, so "one row per type+session+no-semester" isn't an expressible constraint). This surfaced as a real `tsc` type error (`upsertTimeFrame`'s `where` clause) while wiring up DAPU's write path, not as a design review — the nullable field was already live in the pushed schema.
- **Chosen option**: Made `semesterId` required (`Semester`, not `Semester?`). Every one of the five timeframe types this system actually implements is per-semester in practice, so nothing that already worked broke.
- **Reason**: The nullable version was speculative flexibility for a case (a timeframe with no semester) that doesn't occur anywhere in this implementation, and it was actively broken for the case that does occur. Fixing the type to match actual usage removed a Prisma-level footgun rather than working around it.
- **Consequences**: If a genuinely session-wide (not per-semester) deadline type is ever needed, it needs its own handling — either a sentinel "all semesters" `Semester` row, or a separate model — rather than `semesterId: null` on this one.
- **Alternatives rejected**: Dropping `semesterId` from the `@@unique` (keeping just `type + academicSessionId`) — rejected because it would make "one Course Registration deadline per session" true instead of per-semester, which doesn't match how registration actually works (First and Second Semester need independent windows).
