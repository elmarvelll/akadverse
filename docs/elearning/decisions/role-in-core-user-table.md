# Decision: The academic `role` enum extends the Core `User.role`, not a separate E-Learning field

- **Date**: 2026-09-14.
- **Context**: §5 asks for `STUDENT/FACULTY/HOD/DAPU/DEAN/VC` as "the user's primary identity within AkadVerse." The Core `Role` enum (`prisma/schema.prisma`) already had `student/faculty/admin/super_admin` for Marketplace. E-Learning's own database has no `User` model at all (see [`separate-elearning-database.md`](separate-elearning-database.md)).
- **Problem**: Where does the expanded role list live — extend the existing Core `Role` enum, or add a second, E-Learning-only role concept keyed by `userId` in the E-Learning database?
- **Presented to the user as an explicit choice** (not decided unilaterally): extend Core `User.role`, vs. a separate E-Learning-only role field. The user chose the former.
- **Chosen option**: Added `hod`, `dapu`, `dean`, `vc` to the existing Core `Role` enum. `admin`/`super_admin` stay Marketplace-only concepts (Marketplace admin access is actually the independent `User.isAdmin` flag, unrelated to this enum) — they are not part of the academic hierarchy and were left alone.
- **Reason**: `role` is meant to be **one** AkadVerse-wide identity (§45's "ONE AkadVerse identity") — it's what `src/proxy.ts` already used to route a signed-in user home and to gate Marketplace to students-only (§9) before E-Learning existed at all. A second, E-Learning-only role field would let the two systems' idea of "who is this person" drift out of sync (e.g. a user whose Core role says `student` but whose E-Learning role says `faculty`), which is exactly the kind of dual-source-of-truth bug §34's "never trust... anything client-controllable" is meant to prevent at the data level, not just the API level.
- **Consequences**: The Core/Marketplace schema — otherwise meant to stay untouched by this work (§42) — got one additive migration (four new enum values, pushed via `prisma db push`, no data migration needed). Every future role check across both domains reads the same `session.user.role`.
- **Alternatives rejected**: A separate E-Learning role/identity table keyed by `userId` — rejected because it would require every authorization check (Marketplace's student-only gate included) to consult two systems' idea of role and reconcile disagreements, for no benefit over a single enum.
