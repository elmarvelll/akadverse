# Decision: The dev-test account tests roles via separate real accounts, not a runtime override

- **Date**: 2026-09-14.
- **Context**: §7 requires the `marvelousifezue31` account to be able to test every E-Learning role during development, while explicitly forbidding this from becoming a production authorization mechanism ("Do NOT allow a production user to simply select ... from a dropdown and gain that role").
- **Problem**: How does one test account plausibly act as six different roles without a special-cased runtime role-switcher (a cookie, a header, a query param) that itself becomes exactly the kind of "trust the client" mechanism §7 warns against?
- **Chosen option**: The account-type domain selector already required by §8 naturally produces a *different email address* per selection (`marvelousifezue31@stu.cu.edu.ng`, `@faculty.cu.edu.ng`, etc.) — and therefore a different Core `User` row. `src/app/api/register/route.ts`'s narrowly-gated exception (`NODE_ENV !== "production"` **and** local part exactly `marvelousifezue31`) assigns the role matching the signup domain, instead of the usual `student` default, for that one local part only. The tester then has up to six real, separately-stored accounts, each with a real role checked the normal way — no runtime override code exists anywhere in the request path for reads.
- **Reason**: This reuses infrastructure §8 already required (the domain selector) instead of adding new, override-specific infrastructure. It also means there is genuinely no code path, anywhere, that reads a role from something other than the stored `User.role` — the "production authorization must come from the user's stored role" half of §7 is true unconditionally, not true-except-for-a-flag.
- **Consequences**: Testing a new role requires a real signup (or `scripts/elearning-seed.ts` linking an E-Learning profile afterward) rather than a one-click switch — slightly more setup per role, in exchange for zero override surface area. Six separate password/session states to juggle while testing multi-role flows (e.g. registration approval chains) rather than one account switching context.
- **Alternatives rejected**: A dev-only cookie/header read by `src/proxy.ts` or `requireElearningRole` to override the effective role for that one account — rejected specifically because, even gated by `NODE_ENV`, it adds a role-reading code path that doesn't read from `User.role`, which is the exact shape of thing §7 says not to build.
