# Decision: E-Learning gets its own database and Prisma client

- **Date**: 2026-09-14.
- **Context**: The existing/main database holds Core identity (`User`, `Account`, `Session`, `VerificationToken`) and every Marketplace model. §2/§3/§36 asks for E-Learning as a separately-scalable domain.
- **Chosen option**: A second Postgres database (`ELEARNING_DATABASE_URL`/`ELEARNING_DIRECT_URL`), a second Prisma schema (`prisma/elearning/schema.prisma`) with its own generator `output`, and a second client singleton (`src/lib/db/elearning.ts`). No database-level foreign key to the Core database; every reference is a plain `userId` string resolved at the application layer (`services/e-learning/shared/identity.ts`).
- **Reason**: Matches the spec's explicit architecture target exactly (§43/§45) and avoids the two failure modes it warns against: an ever-growing single schema that couples Marketplace and academic concerns, and a cross-database transaction/relation that isn't actually possible between two separate Postgres instances.
- **Consequences**: Identity lookups (a lecturer's name, a student's name for a roster) require an extra query into the Core database via `identity.ts` rather than a Prisma `include`. Migrations for the two domains are run independently (`npm run db:elearning:*` vs. the default `prisma db push`/`migrate`). A user's E-Learning profile can exist without a valid Core `User` row if one is deleted directly in the Core database — there's no cascade; cleanup would be an application-level job if this becomes a real concern.
- **Alternatives rejected**: One combined schema with a Marketplace-DB foreign key from E-Learning tables — rejected outright by the spec (§35) and would make the two domains' migrations, connection pools, and eventual scaling permanently coupled.
