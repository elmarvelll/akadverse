# E-Learning — Architecture

## Two databases, two Prisma clients

```text
AkadVerse
│
├── Core Identity + Marketplace ── existing DB ── prisma/schema.prisma ── @prisma/client (src/lib/prisma.ts)
│
└── E-Learning ──────────────────── separate DB ── prisma/elearning/schema.prisma ── generated/prisma-elearning (src/lib/db/elearning.ts)
```

- `prisma/schema.prisma` (unchanged in shape, only extended — see below) is the Core/Marketplace database: `User`, `Account`, `Session`, `VerificationToken`, and every Marketplace model. Client: `@prisma/client`, imported via `src/lib/prisma.ts`.
- `prisma/elearning/schema.prisma` is a **separate database** (`ELEARNING_DATABASE_URL`/`ELEARNING_DIRECT_URL` in `.env`), with its own generator `output` (`src/generated/prisma-elearning`, gitignored — regenerated by `postinstall`/`build`). Client: `elearningDb`, imported via `src/lib/db/elearning.ts`. **Never** import `@prisma/client` from `services/e-learning/**`, and never import the generated E-Learning client from Marketplace code.
- `npm run db:elearning:{generate,push,migrate,studio,seed}` — see `package.json`. The main `build`/`postinstall` scripts generate both clients.

There is no database-level foreign key between the two — impossible across separate Postgres instances, and not attempted even conceptually (§35/§38, no cross-database transactions either).

## Identity: one Core `User`, no duplication

Every E-Learning profile (`StudentProfile`, `FacultyProfile`, `HodProfile`, `DapuProfile`) stores only `userId` — the Core database's `User.id` — as a plain string, not a relation. `role` itself (`student | faculty | admin | super_admin | hod | dapu | dean | vc`) lives **only** on the Core `User` table; the E-Learning schema has no role/identity concept of its own. This was an explicit decision (not the only option) — see [`decisions/role-in-core-user-table.md`](../decisions/role-in-core-user-table.md).

When E-Learning code needs a name/email for display (a lecturer's name on "My Courses", a student roster), it goes through **one sanctioned module**: `services/e-learning/shared/identity.ts` (`resolveIdentity`/`resolveIdentities`/`fullName`) — the only file under `services/e-learning/` that imports the Core Prisma client. Every other module reaches identity information through this file, never by importing `@/lib/prisma` directly. `scripts/elearning-seed.ts` is the one other place that touches both databases, for the same reason (resolving the dev-test account's Core `User.id` before writing E-Learning profile rows).

## Authorization — four layers, in order

1. **`src/proxy.ts`** (Edge runtime, no Prisma) — reads the signed session JWT's `role` claim only:
   - Redirects `/` to the role's home (`ROLE_HOME_PATHS`).
   - Blocks any non-`student` from `/studashboard/marketplace*` and `/api/marketplace*` (§9).
   - Blocks a mismatched `/e-learning/<role>/...` or `/api/elearning/<role>/...` URL segment — the role in the path is never trusted, only compared against the token's real role.
2. **`src/app/e-learning/layout.tsx`** (server component) — re-derives the session via `requireElearningSession()` and redirects to `/login` if it fails; defense in depth in case the proxy is ever bypassed or misconfigured (§34's "never rely on the URL alone").
3. **Per-page/per-action role check** — every page and every Server Action calls `requireElearningRole([...])` (`services/e-learning/shared/auth.ts`) before touching data.
4. **Scope check** — role alone isn't authorization for anything department/course/student-specific. Every module that needs narrower scope re-derives it server-side from the caller's own profile and re-verifies the resource actually belongs to that scope, rather than trusting an id the client sent:
   - `requireStudentProfile` / `requireFacultyProfile` / `requireHodProfile` / `requireDapuProfile` / `requireLevelAdviserProfile` (`services/e-learning/shared/auth.ts`) resolve *whose* profile is acting.
   - `assertAssignedToCourse` (`services/e-learning/faculty/assigned-courses.ts`) and `requireMySubject` (`faculty/my-subjects.ts`) — a faculty member can only view/upload/enter-results for a course they are assigned to (a `CourseOfferingLecturer` row) this session/semester.
   - Level Adviser and HOD registration/approval functions (`services/e-learning/level-adviser/registrations.ts`, `services/e-learning/hod/registration-approvals.ts`) re-look-up the student's `StudentProfile.departmentId`/`level` and compare against the adviser's/HOD's own profile before allowing an approve/reject.
   - HOD assignment functions (`services/e-learning/hod/course-offerings.ts`, `hod/level-advisors.ts`) re-check that a course/faculty member actually belongs to `hod.departmentId` before writing.

A form field's `courseId`/`registrationId`/`facultyUserId` is always routing information only — every Server Action re-derives the session and re-runs the scope check named above rather than trusting the value.

**Known rough edge**: an authorization failure currently surfaces as an unstyled 500 page (a thrown `ServiceError` in a server component, not caught into a friendly boundary) rather than a polished "forbidden" screen. It's correctly *rejected*, just not nicely presented — see [`todo/roadmap.md`](../todo/roadmap.md).

## Service layer

Business logic lives in `services/e-learning/`, split by role tier (`shared/`, `dapu/`, `hod/`, `level-adviser/`, `faculty/`, `student/`), one capability per file, and imported as `@/services/e-learning/...`. Pages and actions are thin callers. The full map, import rules and "how to add a service" are in [`services.md`](services.md).

## Route structure

```text
/e-learning
├── student/{dashboard,my-learning,my-learning/[courseId],academic-records/*,course-control/*}
├── faculty/{dashboard,my-subjects,my-subjects/[offeringId],results,results/[courseId],level-adviser/*}
├── hod/{dashboard,curriculum/*,assignments/*,approvals/*,results/*}
├── dapu/{dashboard,course-structure/*,timeframes/*,timetable/*}
api/e-learning/documents/[id]/access   (signed URL for a course document)
├── dean          (placeholder)
└── vc            (placeholder)
```

`src/app/e-learning/layout.tsx` renders the shared Header + Sidebar shell for every route above. The nav tree per role lives in `src/app/e-learning/_components/nav-config.ts`; `Sidebar.tsx` is a client component that **builds its own nav tree from plain `role`/`isLevelAdviser` props** rather than receiving a built tree from the server layout — lucide-react icon components can't cross the server→client prop boundary (React error: "Functions cannot be passed directly to Client Components"). This was a real bug caught by testing, not a preemptive design choice — see [`todo/roadmap.md`](../todo/roadmap.md)'s log if a similar pattern is being added elsewhere.

## Login / signup — account-type domains

`src/lib/account-domains.ts` holds the four `role → email domain` mappings from §8 (`stu.cu.edu.ng`, `faculty.cu.edu.ng`, `HODEIE.cu.stu.ng` — deliberately left as spec'd despite looking inconsistent, `DAPU.cu.edu.ng`); VC/Dean are not selectable. On `/signup` a separate Role dropdown fixes the domain shown by `EmailDomainInput` (`src/app/components/email-domain-input.tsx`); `/login` is a plain any-email form with no role/domain picker. See [`systems/authentication-and-domains.md`](systems/authentication-and-domains.md) for the full login/signup/role-assignment behavior, including the one narrowly-gated dev-only exception.
